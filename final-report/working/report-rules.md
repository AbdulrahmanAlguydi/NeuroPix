# NeuroPix report working rules

Consolidated on 18 September 2026 and updated for release on 19 September 2026. Read with `format-specification.md` and `user-manual-changes-2026-09-19.md`. Later explicit user decisions take precedence over older planning notes.

1. Treat the current repository code as the technical source of truth.
2. Use the SRS and HLD for context and reusable diagrams only after checking every claim against the code.
3. Follow the supervisor's required chapter structure and the official cover-page design.
4. Do not invent requirements, testing results, performance figures, user research, citations, or implementation details.
5. Report test results only after the relevant tests have been executed and their output recorded.
6. Keep credentials, environment values, private keys, and other sensitive information out of the report workspace and screenshots.
7. Use IEEE citations and keep a traceable record of each factual source.
8. Use actual application screenshots. Redact sensitive information before inserting them.
9. Create diagrams from verified implementation flows and label inferred details clearly.
10. Run the Humanizer review after substantive drafting without weakening technical accuracy.
11. Preserve the university template's visual identity while correcting layout defects when necessary.
12. Keep routine drafting and revision in DOCX without intermediate PDF export. Inspect significant changes in Word and reserve full PDF rendering for the submission-ready final revision.
13. Use Calibri at 12 pt as the default body font. Headings may use larger sizes for hierarchy while remaining in Calibri unless an official template element must be preserved.
14. Configure the Word `Heading 1` style with `page break before` so every chapter and other Heading 1 section begins on a new page.
15. Perform a visual application UI review after significant interface, layout, workflow, screenshot, or responsive-design changes. Minor text-only changes do not require a new UI review unless they cause wrapping or layout movement.
16. Use the verified HLD cover information in `docs/HLD Senior Project.pdf` for student names, university IDs, project title, and supervisor name; preserve the approved values in the final Word cover.
17. Use `2026` as the academic year. Do not present it as a range or substitute a template year.
18. Execute the six principal use-case tests against the live `https://neuropix.me` deployment in Google Chrome when its required services are available, and clearly label any local fallback or blocked test.
19. Capture a labeled Chrome screenshot after every numbered, user-visible use-case step while reusing setup through explicit preconditions to avoid duplicated login, upload, and data-creation evidence.
20. Keep the bibliography minimal: begin with the repository, SRS, and HLD, then add an external source only when those project artifacts cannot support the claim. Do not add separate references merely to enumerate software dependencies or informal service evaluations.
21. Treat `final-report/` as a local report workspace that is not part of the NeuroPix repository even though it is located inside the repository directory. Never stage, commit, or push this folder, and do not push any repository changes while producing the report.
22. Use the connected Chrome extension as the primary live-testing route. Drive the real Chrome tab with semantic locators, capture screenshots from that same tab, and keep a fixed 1920 x 1080 browser content viewport at 100 percent zoom. Use an independent Playwright browser only as a documented fallback.
23. Keep the related-systems study limited to Adobe Photoshop and Canva, using one current official source for each.
24. Present simplicity and easy browser access as NeuroPix's main advantages within the supported project scope. Avoid claiming that it is more powerful than Photoshop, Canva, or OpenAI's own interface.
25. Describe structured pre-prompting exactly as implemented: the OpenAI path adds preservation rules, field-specific scope rules, and source aspect-ratio context, while the local Stable Diffusion path receives only the user's nonempty text.
26. Use diagrams for internal processes and relationships, screenshots for visible interface evidence, and tables for repeated comparisons or fields. Avoid unnecessary duplication and cross-reference existing visuals. The approved exception is reuse of selected live screenshots in the three Chapter 5 interface figures and their Chapter 6 test evidence; these serve different purposes.
27. Keep the six live use-case tests as the primary report evidence. Add only a one-third- to one-half-page unit/API-level summary using one compact results table; do not add a test inventory, automated-testing appendix, screenshots, code excerpts, or unit-test sequence diagrams.
28. Do not create a formal requirements traceability matrix. Each use-case test should instead state the implemented functionality it covers.
29. Preserve the approved content and readable typography. The latest single-column screenshot layout is 57 pages, including eight preliminary pages. Keep Chapter 2 short, Chapter 7 concise, references to one page, and omit an appendix. Avoid extra pages from preventable layout gaps, but do not shrink text or evidence just to meet an earlier page estimate.
30. Describe the six live tests as verification of the principal user workflows, not as exhaustive proof of every low-level functional or nonfunctional requirement.
31. Retain the Chapter 3 activity diagram, frontend navigation diagram, storage-flow diagram, and four design-level sequence diagrams because they replace explanatory prose and improve readability.
32. Use three multi-panel interface figures in Section 5.7 and omit the appendix entirely unless the supervisor later requests a specific supporting item.
33. Preserve the 62-word abstract explicitly accepted by the user on 18 September 2026. This is an approved exception to the earlier approximate 50-word target. Keep the problem, purpose, approach, and high-level outcome, with exact test counts and timings in Chapter 6 and detailed stack information in the body chapters.
34. Cover every mandatory supervisor-template item even when sections are consolidated: intended-user characteristics, requirements-identification method, mandatory software/hardware requirements, functional and nonfunctional requirements, architecture, interface/component design, implementation requirements and details, I/O screens, a concise test plan, test cases, results, evaluation, six-month future work, IEEE references, and appendix rules.
35. Reconcile generic template advice with the supervisor's later project-specific direction: present the six live use cases as combined functional and acceptance testing and keep their detailed evidence in Chapter 6.
36. Present every screenshot in a single-column row at full text width. Embed full-resolution captures and resize only through Word's displayed dimensions. Label Chapter 6 screenshots with the use-case ID, `(a)` through `(d)`, and a short description. Keep each screenshot with its label; test groups may span pages. Keep each Chapter 5 two-image figure on one page with its introduction and caption.
37. Use DOCX as the editable review master and PDF as the final submission format. Do not export intermediate PDFs during routine revisions. Once the report is submission-ready, update every Word field, remove unresolved editorial markup, disable image compression, export directly at Standard or high quality rather than printing to images, and render-inspect every final PDF page before delivery.
38. Include a technical detail only when it explains architecture, user-visible behavior, an important decision, a tested result, a security control, or a meaningful limitation. Omit library internals, routine coding mechanics, duplicated field lists, encoding steps, and unexplained constants that do not help the reader evaluate NeuroPix.
39. Do not narrate a visual point by point. Diagrams carry structure, relationships, and order; screenshots carry visible interface state; and tables carry repeated fields. Prose should add rationale, interpretation, limitations, or conclusions that the visual does not already communicate.
40. Omit routine temporary-file-cleanup discussion, as requested. Temporary staging may still be explained where it distinguishes upload from persistence. Keep the meaningful cross-service recovery limitation separate; do not claim that cleanup is absent from the code.
41. Use the website accent `#6D5DFC` for both cover-title lines and all headings, with consistent bolding. Use the same accent for data-table header fills with bold white text.
42. Use smaller gray figure/table captions: 9.5 pt, `#5F6368`. Keep caption names concise enough for the automatic lists. Preserve the user's current 11 pt data-table text, alternating white/`#F7F7FF` body rows, and content-based column widths rather than equal divisions.
43. Use built-in Word lists and no positive first-line body indents. Keep tables on one page where practical and keep headings, introductions, figures, and captions together without adding preventable pages or shrinking readable content.
44. Keep the TOC to two pages and each figure/table list to one page. Match their entry spacing where practical (current treatment: 11 pt, single spacing, 2 pt after). Check apparent spacing visually or by pixel measurement rather than trusting style values alone.
45. Write in a natural university-student voice. Use we/our for documented team decisions. Avoid repetitive semicolons, staged contrasts such as 'The problem is not X; it is Y', inflated claims, filler, and point-by-point narration of visuals. Do not impose a blanket ban on useful punctuation or genuine technical distinctions.
46. After substantial prose changes, apply Humanizer, perform a separate meaning/placement review, then check pagination and affected rendered pages. Do not claim that editing guarantees an AI-detector result.
47. Do not include Group 2, the current commit identifier, reference access-date suffixes, a formal traceability matrix, an appendix, or a guest-editing decision comparison. Keep publication dates and internal source-verification dates when useful.
48. Identify the configured OpenAI default (`gpt-image-2.5-sunburst`, unless overridden) and Stable Diffusion 1.5 in Section 5.4. Explain the RTX 3080 constraint and model-selection reasons in the development-decisions discussion without adding low-level precision or inference tutorials.
49. Keep development choices concise (roughly 1–1.5 pages): cost first, student offers, AWS familiarity/resources/CV value, Namecheap's free student domain versus AWS trial limits, the new OpenAI model, local GPU trial costs/friction, and the team's simplified work on main. Present Camber and Lightning.ai as evaluated options, not deployed services. Reverse SSH belongs in deployment and must appear in its diagram.
50. For diagrams, prioritize readable text, safe cropping, sufficient contrast, clear labels, and connectors that do not pass through nodes. Remove excessive outer whitespace and unused sequence tails. Prefer stick-figure user actors where appropriate. Inspect changed diagrams at enlarged size before inserting them into Word.
51. Preserve the approved fidelity corrections: EC2 reverse-tunnel endpoint 8001 versus local service 8000; cached dashboard data followed by gallery API refresh; and Standard editor returns a Pillow image while the route writes JPEG. Do not silently expand the report with previously deferred low-level fidelity findings.
52. Use the violet accent selectively to emphasize important diagram nodes and related arrows. It is editorial emphasis, not a separate operation type or formal UML category. Keep equivalent Standard-processing nodes neutral; use equal accent on their connectors as permitted by rule 57, without arbitrarily highlighting brightness/exposure. Preserve meaningful solid/dashed line styles regardless of color.
53. Update the maintained draft, current decisions, relevant specification/outline notes, checklist, and progress/QA records after revisions. Preserve older evidence with clear historical labels. Tie reused render evidence to the exact DOCX bytes, and record unresolved deviations instead of weakening a rule to manufacture a pass.
54. When an established report treatment is clearer than an earlier outline detail, update the outline instead of expanding or degrading the report to match it. Preserve supervisor-required coverage, verified meaning, and explicit user decisions. Independently make bounded improvements and record their rationale.
55. For the current all-diagram color review, show a separate preview set and await user approval before inserting it into Word or PDF. Meaningful special cases may receive the accent color when there is no natural focal operation. Do not force decorative emphasis or change the diagram's technical meaning.
56. Choose each diagram's accent by reading its containing section and explanatory paragraph first. Emphasize the information that paragraph teaches, not merely a generally important component. In use-case test figures, prioritize the expected action/result over internal mechanisms that the live evidence does not independently verify. Keep section numbers distinct from figure numbers. For Figure 1.1, emphasize the NeuroPix workflow and account workspace while keeping every arrow neutral.
57. Equal accent on every Standard-processing connector is permitted to trace the workflow without ranking operations. Include relevant initiating actions and successful returns, not only endpoints. Distinguish editing the same staged source again from using a processed result as the next source, which requires gallery reload. Keep the GPU model in hardware/deployment discussion rather than the local use-case participant label. Stage substantive diagram/paragraph improvements for preview approval before changing final deliverables.
58. Comparable editing tests should accent corresponding engine requests, image returns, and comparison results. Keep provider-specific preparation, storage, and transport neutral unless those are the section's subject. In the combined authentication design sequence, show user initiation of both registration and login and give their key account/security steps comparable emphasis without coloring routine API/lookup messages.
59. Review every diagram at three levels: technical accuracy, agreement with its containing section, and its role in the report as a whole. Keep design explanations distinct from tested evidence, and future improvements distinct from implemented behavior. Preserve consistent source reuse, ownership, registration/session, provider-prompting, and tunnel-direction explanations across chapters. Do not remove useful diagrams merely because another chapter discusses the same feature from a different perspective.

60. Give dense adjacent table rows breathing room through top/bottom cell padding, not blank paragraphs or forced equal heights. Current default is 4 pt per side; Table 1.1 retains 2.5 pt to preserve its subsection grouping. Review actual rendered widths, heights, and pagination after changes. Keep font sizes readable and allocate more width to text-heavy columns.

61. Preserve the user's saved manual Word revision as the master. Its crops, image dimensions, table grids/shading, 11 pt table/reference text, bullet indentation, manual line breaks, and selective bolding supersede older build settings. Make targeted edits rather than regenerating from earlier drafts. Detailed record: `user-manual-changes-2026-09-19.md`.

Completion note, 19 September 2026: the user approved revision 5, fulfilling the preview gates in rules 55 and 57. All 20 diagrams and the reviewed prose are published in the final DOCX/PDF. Historical QA renders and intermediate versions were removed for repository release; the current deliverables, figures, sources, and durable decision records remain. The standing rules above still apply to any future revision.
